# 《数据挖掘》探索性实验报告

## 实验项目3：游览路线的层级结构挖掘

### 实验说明

本实验使用任务一清洗结果 `data/processed/clean_documents.json`，对故宫路线文本进行解析，统一表示为有序路线步骤，并进一步构建时间层级。实验使用的文档如下：

| 文档 | 来源性质 | 用途 | 处理结果 |
|---|---|---|---|
| `GG_F01` | `official_route_facts` | 官方推荐路线事实记录 | 解析 12 个有序步骤 |
| `GG_S01` | `synthetic_teaching` | 分时编号路线教学样例 | 解析 9 个步骤，仅用于验证分时格式 |
| `GG_T01` | `dataset_corpus` | 游客游记中的分时叙述 | 人工证据标注 13 个步骤 |
| `GG_T05` | `dataset_corpus` | 游客游记中的实际路线叙述 | 人工证据标注 5 个步骤，用于路线对比 |

`GG_F01` 是带参考链接的路线事实记录，不等同于已独立核验的官网全文；`GG_S01` 是教学模拟数据，不作为真实旅游事实；`GG_T01` 和 `GG_T05` 是数据集中的游客语料。报告对这些来源进行区分，不把模拟数据或整理稿表述为真实官方原文。

## 3.1 路线描述模式与输入范围

### 3.1.1 路线描述模式

本实验观察到三类路线表达。

**（1）连接符链路**

`GG_F01` 中的典型片段为：

> 推荐行进顺序：午门-太和门-弘义阁(皇朝礼乐展)-太和殿-中和殿-保和殿-乾清门-乾清宫-交泰殿-坤宁宫-御花园-神武门。

该格式以景点顺序为核心，景点之间使用 `-`、`→`、`➜`、`⟶` 或 `->` 连接。括号内容可能是展览或活动，例如 `弘义阁(皇朝礼乐展)`，不能直接当成一个复合景点名称。

**（2）按时间段组织的编号列表**

`GG_S01` 中采用“时间段标题 + 编号 + 起止时间 + 地点 + 活动”的形式，例如：

> 上午：  
> 1. 09:00—09:20，午门：入院与导览。  
> 2. 09:20—10:00，太和殿：参观主体建筑。

该格式同时包含时间层级、具体时刻、地点、活动和顺序，是构建时间层级的主要输入。

**（3）游客游记自然叙述**

`GG_T05` 中的典型片段为：

> 从午门走进故宫。一路欣赏着，来到了太和殿前。我们游览了干清宫的雄壮气势。紧接着，我们来到了故宫珍宝馆。从故宫南门进，从北面的神武门出了。

自然叙述不一定有统一句式。地点被提及不代表游客实际到访，且同一地点可能多次出现。因此，本实验不使用简单关键词扫描推断完整路线，而是对具有明确“进入、到达、游览、离开”语义的原句进行人工证据标注。

### 3.1.2 解析难点与支持范围

主要难点包括：

1. 连接符可能有多种写法，且中文短横线也可能出现在普通文本中；
2. 括号内容可能表示展览活动，而不是新的景点；
3. 编号列表的顺序、时间和时间段标题需要保持一致；
4. 游记中的邻近地点只是背景提及，不能全部加入路线；
5. 官方资料、模拟资料和游客资料的来源性质不同，不能混合解释。

当前程序明确支持：

- 连接符路线：支持 `-`、`→`、`➜`、`⟶`、`->`；
- 编号分时路线：支持“上午/中午/午间/下午”标题，以及 `序号. 起始时间—结束时间，地点：活动`；
- 游客自然叙述：支持经过人工审核的证据标注，并要求原句能够在清洗文本中定位。

核心实现位于 [`routes.py`](../../../src/tourism_mining/domain/routes.py)，路线编排位于 [`route_mining.py`](../../../src/tourism_mining/services/route_mining.py)。

## 3.2 统一结构化表示与解析程序

### 3.2.1 统一路线结构

每条路线统一表示为一个 JSON 对象，主要字段如下：

| 字段 | 类型 | 含义与缺失处理 |
|---|---|---|
| `route_id` | 字符串 | 路线稳定标识 |
| `scenic_name` | 字符串 | 归一化后的景区名称 |
| `route_kind` | 字符串 | 官方事实、模拟样例或游客实际路线 |
| `document_id` | 字符串 | 输入文档标识 |
| `provenance_kind` | 字符串 | 数据来源性质 |
| `parse_method` | 字符串 | 使用的解析方法 |
| `steps` | 数组 | 按路线顺序排列的步骤 |
| `time_hierarchy` | 对象 | `morning`、`noon`、`afternoon`、`unknown` 四层 |

每个 `steps` 元素包含：

| 字段 | 类型 | 含义 |
|---|---|---|
| `order` | 整数 | 从 1 开始的路线顺序 |
| `poi` / `poi_id` | 字符串 | 规范化景点名及景区内稳定标识 |
| `poi_kind` | 字符串 | `named_poi` 或 `descriptive_location` |
| `raw_label` | 字符串 | 输入中的原始地点名称 |
| `activity` | 字符串或空值 | 展览、参观、休息等活动 |
| `step_type` | 枚举 | `entry`、`visit`、`exit` |
| `time_slot` | 枚举 | `morning`、`noon`、`afternoon`、`unknown` |
| `time_start` / `time_end` | 字符串或空值 | 原文明确给出的起止时间 |
| `time_source` | 字符串 | 时间来源说明 |
| `source_quote` | 字符串 | 可复核的原文片段 |
| `source_span` | 对象或空值 | 在 `clean_content` 中的字符区间 |

缺失时间不补造。没有时段的步骤使用 `time_slot: "unknown"`；没有具体时刻时，`time_start` 和 `time_end` 保持空值。模拟数据中的时间也只标记为来源明确的教学样例，不外推为真实开放时间或停留时长。

### 3.2.2 核心解析流程

1. 读取并校验 `clean_documents.json`，检查文档为数组、`doc_id` 唯一且 `clean_content` 为字符串；
2. 根据路线类型选择解析器；
3. 解析地点、活动、顺序及时间字段；
4. 对名称进行规范化，但保留 `raw_label`；
5. 记录原文证据和字符区间；
6. 按时间段生成 `time_hierarchy`；
7. 校验步骤连续性、证据位置和归一化结果；
8. 输出 JSON、CSV 和运行清单。

对应实现：

- [`parse_official_chain`](../../../src/tourism_mining/domain/routes.py)：连接符路线；
- [`parse_numbered_timed_route`](../../../src/tourism_mining/domain/routes.py)：编号分时路线；
- [`parse_annotated_travelogue`](../../../src/tourism_mining/domain/routes.py)：游客证据标注；
- [`write_route_artifacts`](../../../src/tourism_mining/adapters/route_files.py)：产物写出。

### 3.2.3 结构化输出

程序输出以下文件：

- [`routes.json`](./routes.json)：四条路线的统一结构和时间层级；
- [`route_steps.csv`](./route_steps.csv)：路线步骤明细，便于表格核验；
- [`route_comparison.json`](./route_comparison.json)：官方路线与游客路线的对比指标；
- [`run_manifest.json`](./run_manifest.json)：输入文件哈希、来源文档、输出清单和校验状态。

## 3.3 时间层级构建

### 3.3.1 时间划分依据

时间层级只依据文本中明确出现的时间段标题或具体时刻：

- `上午` → `morning`；
- `中午`、`午间` → `noon`；
- `下午` → `afternoon`；
- 没有明确时间 → `unknown`。

具体时刻只在原文提供时写入 `time_start` 和 `time_end`。例如 `09:00—09:20` 被原样保留，不根据景点常识或活动名称推测时间。

### 3.3.2 层级结果

本次实际结果如下：

| 路线 | 上午 | 中午 | 下午 | 未说明 |
|---|---:|---:|---:|---:|
| 官方路线事实 `GG_F01` | 0 | 0 | 0 | 12 |
| 游客路线 `GG_T01` | 9 | 0 | 4 | 0 |
| 游客路线 `GG_T05` | 0 | 0 | 0 | 5 |
| 教学模拟路线 `GG_S01` | 5 | 1 | 3 | 0 |

### 3.3.3 层级结构示例

`GG_S01` 的层级结构为：

```text
故宫教学模拟路线
├── 上午
│   ├── 09:00—09:20 午门：入院与导览
│   ├── 09:20—10:10 太和殿：参观
│   ├── 10:10—10:40 中和殿：参观
│   ├── 10:40—11:20 保和殿：参观
│   └── 11:20—12:00 乾清宫：参观
├── 中午
│   └── 12:00—13:00 乾清宫附近休息点：用餐
└── 下午
    ├── 13:00—14:20 珍宝馆：参观
    ├── 14:20—15:20 御花园：游览
    └── 15:20—16:00 神武门：离院
```

对于没有明确时间的官方路线，所有步骤归入 `unknown`，但仍保留路线顺序。这样既能表达景点先后关系，也不会把缺失信息错误地填成上午或下午。

## 3.4 名称归一化与稳健性

### 3.4.1 名称处理规则

1. **字形或录入变体**：`干清宫`规范为`乾清宫`，但 `raw_label` 保留原始写法；
2. **景区别名**：`紫禁城`、`故宫博物院`可归一为景区名`故宫`，但景区名称归一化与 POI 名称归一化分开；
3. **父区域与子景点**：`宁寿宫区`、`珍宝馆`等保持不同实体，不因空间包含关系合并；
4. **入口俗称与正式地点**：不自动把`南门`等同于`午门`，除非文本或人工证据明确建立关系；
5. **重复地点**：路线中同一 POI 多次出现时，步骤仍保留其行程事件；计算路线覆盖率和对齐率时按不同 POI 去重；
6. **活动与景点分离**：`弘义阁(皇朝礼乐展)`解析为 POI=`弘义阁`、activity=`皇朝礼乐展`；
7. **描述性地点**：`附近休息点`和`前朝三大殿`标记为 `descriptive_location`，不伪装成单个建筑。

### 3.4.2 稳健性边界

程序通过原始名称、规范名称、来源原句和字符区间同时保存信息，避免归一化后无法追溯。对于没有足够证据的简称、同名异地、复杂父子区域和仅在上下文中提及的地点，程序不强行合并或加入路线，而是保留为待人工判断的内容。

当前别名表是针对本次样本建立的小规模规则，不能覆盖所有景区的异名和同名地点。若扩展数据范围，应增加景区限定的别名表、实体层级关系和人工复核记录。

## 3.5 结构结果验证

### 3.5.1 自动验证项目

程序运行时执行以下检查：

1. 输入文档存在，且 `doc_id` 不重复；
2. 每条路线的 `order` 从 1 连续递增；
3. 连接符链路中的步骤顺序与原文顺序一致；
4. 游客标注的 `source_quote` 必须能在 `clean_content` 中精确定位；
5. `source_span` 必须在文本范围内；
6. 时间段只能来自文本明确标题，具体时间不能凭空生成；
7. POI 名称必须经过规范化；
8. 对比指标的分母使用不同 POI 数量，重复经过同一点不会虚增覆盖率。

### 3.5.2 原文到解析结果的追溯例证

**例证一：连接符路线**

| 原文 | 解析结果 | 层级结果 |
|---|---|---|
| `弘义阁(皇朝礼乐展)` | `poi=弘义阁`，`activity=皇朝礼乐展`，`order=3` | `time_slot=unknown` |

括号中的展览没有被错误并入景点名，且该步骤在路线顺序中的位置保持不变。

**例证二：名称归一化**

| 原文 | 解析结果 | 核验 |
|---|---|---|
| `我们游览了干清宫的雄壮气势` | `raw_label=干清宫`，`poi=乾清宫` | 保留原词、规范名和来源区间 |

**例证三：分时路线**

| 原文 | 解析结果 | 层级结果 |
|---|---|---|
| `12:00—13:00，乾清宫附近休息点：休息与自备午餐` | `time_start=12:00`，`time_end=13:00`，`poi_kind=descriptive_location` | `noon` |

### 3.5.3 测试与失败样例

当前测试包括连接符、箭头、括号活动、编号分时、自然叙述证据、时间层级、名称归一化、重复地点指标和完整流水线，共 9 个单元测试及 1 个集成测试，全部通过。

程序会主动拒绝以下输入：

- 找不到“推荐行进顺序”的连接符路线；
- 编号不连续的分时路线；
- 游客标注原句不在清洗文本中；
- 缺少必需输入文档；
- 无法识别的时间层级。

当前已知限制是：自然叙述采用人工审核标注，不能据此宣称实现了自由文本路线抽取准确率；官方路线资料不是独立核验的完整官网正文；真实来源没有可比较的逐点时刻，因此不计算真实停留时长。

## 3.6 官方与游客实际路线对比【附加题】

### 3.6.1 可比路线

本题选择同一景区故宫的两条路线：

- 官方路线事实 `GG_F01`：午门 → 太和门 → 弘义阁 → 太和殿 → 中和殿 → 保和殿 → 乾清门 → 乾清宫 → 交泰殿 → 坤宁宫 → 御花园 → 神武门；
- 游客实际路线 `GG_T05`：午门（入园） → 太和殿 → 乾清宫 → 珍宝馆 → 神武门（离园）。

两条路线都转换为相同的 POI、顺序和步骤结构。游客路线只保留有明确进入、到达、游览或离开语义的节点，不把“附近有某建筑”的背景描述当成实际游览。

### 3.6.2 指标与结果

设官方路线不同 POI 集合为 \(O\)，游客路线不同 POI 集合为 \(T\)，共同 POI 集合为 \(S=O\cap T\)。

1. **官方路线覆盖率**

   \[
   Coverage=\frac{|S|}{|O|}=\frac{4}{12}=33.3\%
   \]

2. **游客路线官方对齐率**

   \[
   Alignment=\frac{|S|}{|T|}=\frac{4}{5}=80.0\%
   \]

3. **共同景点顺序一致性**

   取两条路线共同 POI 序列的最长公共子序列（LCS）：

   \[
   OrderConsistency=\frac{LCS}{|S|}=\frac{4}{4}=100\%
   \]

共同景点为：午门、太和殿、乾清宫、神武门；游客独有景点为珍宝馆；官方独有景点为太和门、弘义阁、中和殿、保和殿、乾清门、交泰殿、坤宁宫、御花园。

以上结果保存在 [`route_comparison.json`](./route_comparison.json) 中，指标计算代码位于 [`compare_routes`](../../../src/tourism_mining/domain/routes.py)。

### 3.6.3 差异原因与可比性限制

游客路线比官方路线短，且额外出现珍宝馆，可能由以下原因造成：

1. 游客游记倾向于记录印象深刻或实际停留的地点，可能省略经过的建筑；
2. 官方路线事实记录强调完整行进顺序，游客叙述强调个人体验，粒度不同；
3. 两条路线来自不同文本来源，路线覆盖范围和记录目的不同；
4. 单篇游客语料不能代表所有游客行为；
5. 官方路线和 `GG_T05` 均没有可比较的逐点时间，因此不对时间分配或停留时长作无依据的推断。

因此，33.3%、80.0% 和 100% 只描述本次选取文本中的结构关系，不代表总体旅游路线规律。
