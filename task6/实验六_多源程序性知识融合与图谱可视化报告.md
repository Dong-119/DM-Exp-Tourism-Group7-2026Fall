# 实验项目6：多源程序性知识的融合与图谱可视化

## 1. 实验目标与输入

本实验将实验二识别的景点、交通和时间实体，实验三解析的官方/游客路线，以及实验五抽取的条件性建议融合为统一知识图谱。图谱以故宫为主要展示景区，同时保留颐和园、天坛和北京通用建议，避免把不同景区的同名实体错误合并。

输入文件：

| 来源 | 文件 | 用途 |
|---|---|---|
| 实验二 | `task2/task2_jieba_final/result/v2/entities_v2.json` | POI、TRANSPORT、TIME 实体及来源 |
| 实验三 | `data/processed/experiment3/routes.json` | 路线步骤、顺序、时间层级和活动 |
| 实验五 | `task5/results/条件建议映射表.json` | 条件、建议、适用景区和游客类型 |

## 2. 多源融合策略

实体使用“类型 + 景区 + 规范名称”对齐。例如故宫的 `poi:故宫:午门`与实验三路线中的午门合并；不同景区的“长廊”不合并。TIME 节点使用全局规范名称，因为“上午”“下午”是跨景区共享的时间层级。

名称合并规则：

1. 优先使用实验二的 `canonical` 和实验三的规范化 `poi`；
2. 保留原始文本、来源文档、来源实验和 `source_kinds`；
3. 条件建议以 `mapping_id` 建立条件和建议节点，避免相同条件文本在不同来源中被错误折叠；
4. 路线重复经过同一点时保留多个 `visits` 和 `next` 关系，但覆盖统计按不同 POI 计算；
5. 空名称、空条件/建议、未知实体类型被过滤并计入诊断。

## 3. 图谱模式设计

节点类型：

| 类型 | 含义 |
|---|---|
| `scenic` | 景区 |
| `route` | 官方、游客或模拟路线 |
| `poi` | 景点或描述性地点 |
| `transport` | 交通实体 |
| `time` | 上午、中午、下午等时间 |
| `activity` | 展览、参观、休息等活动 |
| `condition` | 条件性建议的适用条件 |
| `advice` | 条件满足时的行动建议 |

边类型：

| 关系 | 含义 |
|---|---|
| `contains` | 景区包含 POI；不表示包含时间或交通 |
| `mentions_transport` | 来源文本提及交通方式 |
| `mentions_time` | 来源文本提及时间表达 |
| `has_route` | 景区包含路线 |
| `visits` | 路线访问景点，带顺序和步骤类型 |
| `next` | 路线中相邻景点的先后关系 |
| `occurs_in` | 步骤发生于时间层级 |
| `has_activity` | 景点对应活动 |
| `has_condition` | 景区适用某条件 |
| `recommends` | 条件触发建议 |

## 4. 图谱构建与可视化结果

程序 [`run_experiment.py`](./run_experiment.py) 使用 NetworkX `MultiDiGraph` 构建图谱，输出：

- [`nodes.csv`](./results/nodes.csv)
- [`edges.csv`](./results/edges.csv)
- [`knowledge_graph.json`](./results/knowledge_graph.json)
- [`knowledge_graph.graphml`](./results/knowledge_graph.graphml)
- [`knowledge_graph.svg`](./results/knowledge_graph.svg)
- [`故宫路线结构可视化.svg`](./results/故宫路线结构可视化.svg)：按路线分行的清晰路线图；
- [`故宫条件建议可视化.svg`](./results/故宫条件建议可视化.svg)：条件与建议的代表性关系图。
- [`故宫完整游览知识网络.svg`](./results/故宫完整游览知识网络.svg)：故宫单景区的分层完整知识网络，突出路线、景点和建议链路。
- [`complete_graphs_index.json`](./results/complete_graphs_index.json) 和 [`complete_graphs/`](./results/complete_graphs/)：按关系类型分页的完整关系图集，628 条边全部展示。

如果当前 Python 环境能够正常读取 Matplotlib，还会生成 [`knowledge_graph.png`](./results/knowledge_graph.png)；本次沙箱运行受用户目录权限限制，因此以 SVG 作为可提交的矢量图谱。

可视化以故宫为中心截取两跳邻域，使用颜色区分节点类型，并标注关系类型。路线节点、景点节点和条件建议节点均可辨识；`next` 关系突出路线先后路径，避免将全量 48 篇文章的实体全部挤在一张图中。

原始全图适合展示“图谱规模”，但不适合阅读节点文字。因此报告正文建议优先使用“故宫路线结构可视化.svg”和“故宫条件建议可视化.svg”：前者按路线分行、按顺序编号，后者将条件与建议拆成两列，避免节点和边重叠。

本实验另外提供“故宫完整游览知识网络.svg”作为单景区主图。该图只截取故宫相关节点，按景区、路线、景点、时间、交通、活动、条件、建议分列；保留该子图中的全部关系，节点标签后的数字表示来源频次/合并次数，数值较大的午门、太和殿、乾清宫等为核心节点。横向关系可读为“路线访问景点”“景点先后”“景点发生时间”“景点对应活动”“条件触发建议”等。

两张重点图不代表全部关系。为满足“完整展示”要求，程序另外按关系类型生成完整关系图集：每页最多 40 条边，每行明确显示“源节点 → 关系 → 目标节点”，并保留顺序、来源文档等属性。`complete_graphs_index.json` 记录页码、关系类型和边号范围，验证程序检查图集边数与图谱边数一致。

## 5. 验证与分析

运行后 [`validation.json`](./results/validation.json) 检查：

1. 八类节点是否存在；
2. 是否产生路线相邻 `next` 关系；
3. 边是否保留 `task2/task3/task5` 来源；
4. 图是否形成有效连通分量；
5. 每条路线是否至少连接一个景点。

`run_manifest.json` 保存三个输入文件的 SHA-256、节点/边数和验证结果。核心节点按度数排序，可以识别景区中心、路线节点以及被多条关系引用的 POI。典型路线可沿 `scenic -> route -> poi -> next -> poi` 查询；条件建议可沿 `scenic -> condition -> advice` 查询。

实体对齐和去重采用“类型 + 景区 + 规范名称”：故宫的“干清宫”和“乾清宫”按实验三规范名对齐，保留原始标签和来源；不同景区的同名景点不合并；条件建议按 `mapping_id` 保留每条规则。实验二与景区同名的冗余 POI 候选被过滤，空实体、未知类型、空条件/建议被诊断并排除。节点的 `source_count`、`source_kinds`、`source_documents` 和边的 `source_type`、`source_document` 保留合并依据，可解释为什么合并或保留。

本次运行中，240 个冗余景区同名 POI 候选被过滤；完整图谱保留 462 个节点、628 条边。故宫主图只截取故宫相关网络，避免颐和园、天坛节点造成遮挡；同时保留完整关系图集，覆盖全部 628 条边。核心路径包括：

```text
故宫 → 官方路线 → 午门 → 太和门 → 弘义阁 → 太和殿 → 中和殿
```

以及：

```text
故宫 → 条件 → 建议
```

需要注意：实验二实体是跨文章出现次数的候选集合，实验三路线是结构化路线事件，实验五建议包含教学模拟语料。因此图谱保留 `provenance_kind` 和 `source_type`，不能将所有边解释为同等强度的现实事实。实验二的交通和时间只表示“文本提及”，分别使用 `mentions_transport` 和 `mentions_time`；它们不表示景区包含交通或时间，也没有被虚构为某两个景点之间的交通路径。实验二中与景区同名的冗余 POI 候选会被过滤，因为景区节点已经承担该实体的表示。

## 6. 复现命令

```powershell
python -m pip install -r task6\requirements.txt
python task6\run_experiment.py
```

生成结果后，可用 NetworkX、Gephi 或 Neo4j 导入 `knowledge_graph.graphml`；CSV 文件也可作为 Neo4j 节点/关系批量导入数据。程序完成后应看到 `validation.passed` 为 `true`。
